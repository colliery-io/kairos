# Triage

Run the delivery board's backlog grooming ceremony. The board is the state machine: columns **Backlog → Todo → Blocked → Active → Completed**, item types **Task**, **Bug**, **Tech Debt**. Triage moves items Backlog → Todo (or out of the system) and keeps Todo stocked with the next highest-priority work.

Everything triage learns is written onto the items themselves — the board is the record, not the conversation. Notes live under a `## Triage Notes` heading on the item: create the heading on the first append, anchor later `edit_item` calls on it. Every note starts with:

> *This was generated by AI during triage.*

## Invocation

The team lead invokes `/kairos:triage` and describes what they want in natural language. Interpret and act:

- no arguments, or "groom the backlog" — the full ceremony (below)
- "show me what needs attention" — the attention pass only
- "let's look at <short code>" — triage that one item
- "move <short code> to todo" — quick override

Resolve the board with `whoami`/`my_boards` (the user's delivery board) unless the user names one. When the session is wired to a **repository** (the `repository` in the SessionStart context), groom the tasks of this board that link to it by default — `board_items` with `repository=<slug>` — and say so; the lead can widen to the whole board ("groom everything"). A request with no repository is not in the filtered list. Find it on the whole board: `board_items` marks it `[support lane]`. Duplicate searches (`search`) stay board-wide regardless: a duplicate in another repo is still a duplicate.

## Show what needs attention

`board_items` on Backlog and Blocked (`column=Backlog`, then `column=Blocked`). `board_items` gives 200 items at most in one result. When the result is a part of the board, its first lines say so and give the `offset` of the next part. Call `board_items` again with that `offset` until you have each part. The counts of a bucket are the counts of all the parts. Present buckets, oldest first, with counts and a one-line summary per item:

1. **Unrefined** — Backlog items without acceptance criteria
2. **Unprioritized bugs** — Bugs without a priority value
3. **Stale** — Backlog items untouched 90+ days
4. **Blocked** — items in Blocked, with what each is waiting on

Let the lead pick where to start.

Name each item by its short code and the title. Take the column names from the board, not from memory, and translate the lead's words ("ticket", "epic", "sprint") to the Kairos item types: the `kairos-vocabulary` skill and its [ITEM-TYPES.md](../../meta/kairos-vocabulary/ITEM-TYPES.md).

## Triage a specific item

1. **Gather context.** `get_item` for content, metadata, and relationships; `get_history` for prior triage notes so you don't re-ask resolved questions. Note the item's lane and `repository` (`get_item` prints both). A **request** from a different team is in the entry column, in the support lane, and needs no repository. Triage it like any other item; its author owes the answers to "needs info" questions. Check redundancy: `search` the boards for a duplicate item, and search the codebase for an existing implementation of the requested behavior by domain concept, not just the request's wording — report where you looked.
2. **Verify the claim.** For a Bug, reproduce it from the reported steps before anything else; report confirmed (with code path), failed, or insufficient detail. For a Task or Tech Debt item, confirm the premise still holds in the codebase.
3. **Recommend.** Give the lead your recommendation — refine toward Todo, needs info, cancel, or archive — with reasoning and a brief summary of what you found in the codebase. Wait for direction.
4. **Grill if needed.** If the item needs fleshing out, run the `grilling` skill — sharpen it one question at a time, capturing each answer on the item as it lands.
5. **Apply the outcome** (on the item, via `edit_item` / `set_metadata` / `transition_item`):
   - **Refined** — acceptance criteria written (read [ACCEPTANCE-CRITERIA.md](ACCEPTANCE-CRITERIA.md) first), effort and priority set via `set_metadata` on the board's defined scales — ask the lead once for the scale if the board defines none; moves to Todo when it's next in line. A refined item that needs code links to exactly one repository. `set_repository` (`short_code`, `repository`) sets the link and changes nothing else. An item with no code, such as support work, needs no repository. Work that spans repos is split into one task per repo joined by `blocks`/parent edges — never one item that "touches both".
   - **Wrong team** — an item that belongs to another team's board is *moved*, never recreated there (recreating loses its history, its edges, and its author): `move_item` with `to_board` their delivery board. You need `manage_tasks` on both boards, so if the tool refuses, say which board it belongs on and ask the lead. The task keeps its repository: the move does not look at it.
   - **Needs info** — append triage notes: what's established so far, and specific, actionable questions naming who owes the answers. Stays in Backlog; on the next pass, re-read the notes and continue rather than restart.
   - **Cancel** — when the lead rejects the item outright ("won't do"): `cancel_item` with the reason. A cancel needs a reason, and the reason stays on the task; the task goes to the done column, marked Cancelled. If the work comes back later, it is a new task.

## The grooming ceremony

Work the backlog through these actions; the ceremony is done only when every one holds:

1. **Refine.** Every item groomed toward Todo carries acceptance criteria ([ACCEPTANCE-CRITERIA.md](ACCEPTANCE-CRITERIA.md)) and an effort estimate.
2. **Prioritize bugs.** `set_metadata` priority (P0–P3) on every Bug on the board that lacks one. **P0s are pulled immediately** — flagged to the lead in the moment and moved straight to Todo ahead of everything, with expedited acceptance criteria (at minimum the verified reproduction and "no longer reproduces") written as they're pulled; P1–P3 ordered within the backlog.
3. **Weigh tech debt.** Tech Debt flows on a standing allocation of roughly 20% of team time — as an item check, about 1 in 5 items across Todo and Active. Under the allocation → propose promoting the highest-value debt items, lead confirms, until the ratio holds; over → hold debt in Backlog.
4. **Archive stale items.** For each Backlog item untouched 90+ days, propose archival to the lead. On confirmation, append a short note recording *why* it's being archived — durable reasoning, so a returning request meets the recorded decision instead of re-litigation — then `delete_item` with `confirm: true`. This archives the item: `restore_item` brings it back, and the note and history stay. Never use `purge_task` for this: a purge removes the task for good. If the lead wants it kept, append a parked note with the condition that revives it, and it stays in Backlog.
5. **Clear the done column.** When the lead asks, `archive_completed` on the board archives each task in its done column (finished and cancelled). Each one can be restored.
6. **Restock Todo.** Ask the lead once for the target Todo depth (default: one item per team member), then `transition_item` the next highest-priority refined items Backlog → Todo until Todo is at depth.

## Cross-team blockers

When an item waits on another team: `link_items` with relationship `blocks` from the blocking item (theirs) to the blocked item (ours), `transition_item` ours to Blocked, and append an escalation note naming exactly what's needed and from whom — on the item **and** on its parent initiative, so the blocker is visible at the Initiative Board Review, where cross-team blockers are raised publicly. The `blocks` edge plus the initiative note *is* the escalation — there is no side channel.

## Quick override

"Move <short code> to todo" — trust the lead. Confirm what you're about to do (transition, metadata, note), then act, skipping the ceremony. If the item is headed to Todo without acceptance criteria, ask whether to write them first.
